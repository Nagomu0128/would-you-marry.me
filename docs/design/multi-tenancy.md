# テナント分離

## 方針

- 1 つの結婚式を 1 つのテナントとする
- すべてのテナントで同じシステム・同じデータストアを共有し、データにテナント ID を持たせて論理的に分離する
- テナントは UUID で識別する（D-05）

## テナント ID

- UUID v4（ランダム）を使う。テナント ID は参加 URL に含まれて参加者の目に触れるため、作成順や作成日時を推測されない v4 にする
- システムがテナント作成時に採番する（FR-A-03）

## 原則

| # | 原則 | 内容 |
|---|---|---|
| P1 | すべてのデータにテナント ID を持たせる | Tenant 以外のエンティティはすべて `tenantId` を持つ（[domain-model.md](domain-model.md)） |
| P2 | テナントはセッションから決める | 参加者・新郎新婦がどのテナントに属するかは、サーバーがセッションから判断する。URL に含まれるテナント ID は画面の切り替えに使うだけで、セッションのテナントと一致しなければ拒否する |
| P3 | 読み書きは必ずテナント ID で絞り込む | テナントスコープのデータへのアクセスには、必ずセッションのテナント ID を条件に付ける。個々の処理で書き忘れないよう、データアクセスの共通部分で強制する（強制の仕組みは技術選定時に決める） |
| P4 | ファイルもテナントごとに分ける | 写真・席次表 PDF・コース表画像の保存先はテナント単位で分ける（例: `tenants/<tenantId>/photos/...`）。データ削除（FR-A-13）もこの単位で行う |
| P5 | ファイルを公開しない | 写真・PDF・画像は誰でもアクセスできる URL で公開しない。短時間だけ有効な URL を発行するか、アプリケーションを経由して配信する |
| P6 | UUID はアクセス制御ではない | テナント ID を知っていても、有効な参加トークン・新郎新婦用トークンとパスコード・セッションがなければアクセスできない。UUID が推測困難であることに安全性を頼らない |
| P7 | ログにテナント ID を付ける | 外部の監視ツールでテナント単位に絞り込めるようにする（NFR-18） |
| P8 | 管理者はテナント横断 | 管理者はすべてのテナントを操作できる。管理操作は記録する（NFR-19） |

## URL の形式（仮置き）

| 用途 | URL の例 |
|---|---|
| 参加 URL（QR コード） | `https://<ゲスト用ドメイン>/join/<tenantId>?t=<参加トークン>` |
| ユーザー画面 | `https://<ゲスト用ドメイン>/t/<tenantId>/home` など |
| 新郎新婦用 URL | `https://<ゲスト用ドメイン>/couple/<tenantId>?t=<新郎新婦用トークン>` |
| 新郎新婦用ページ | `https://<ゲスト用ドメイン>/couple/<tenantId>/photos` など |
| 管理面 | `https://<管理用ドメイン>/...` |

- 参加トークン・新郎新婦用トークンは、検証後にリダイレクトして URL から取り除く（[auth.md](auth.md)）
- 管理面はユーザー画面・新郎新婦用ページと別のオリジン（ドメイン）で提供し、Cookie などのセッション情報を共有しないようにする

## テナント間アクセスの確認観点

実装後、少なくとも次のことを確認する。

- テナント A の参加者のセッションで、テナント B の URL にアクセスすると拒否される
- テナント A の参加者のセッションで、テナント B の写真を指定した閲覧・いいね・保存・削除が拒否される
- テナント A のタイムラインとランキングに、テナント B の写真が含まれない
- テナント A の参加トークンを使って、テナント B の参加 URL から参加できない
- テナント A の新郎新婦のセッションで、テナント B の写真を閲覧・保存できない
- テナント A の新郎新婦用トークンとパスコードで、テナント B の新郎新婦用ページに入れない
- 写真・PDF・画像の配信 URL を流用しても、有効期限が切れた後はアクセスできない
