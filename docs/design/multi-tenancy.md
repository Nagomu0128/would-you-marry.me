# テナント分離

## 方針

- 1 つの結婚式を 1 つのテナントとする
- すべてのテナントで同じシステム・同じデータストアを共有し、データにテナント ID を持たせて論理的に分離する
- テナントは UUID で識別する（[D-05](../open-questions.md)）

## テナント ID

- UUID v4（ランダム）を使う。テナント ID は参加 URL に含まれて参加者の目に触れるため、作成順や作成日時を推測されない v4 にする
- システムがテナント作成時に採番する（FR-A-03）

## 原則

| # | 原則 | 内容 |
|---|---|---|
| P1 | すべてのデータにテナント ID を持たせる | AdminUser 以外のエンティティはすべて `tenantId` を持つ（[domain-model.md](domain-model.md)） |
| P2 | テナントはセッションから決める | 参加者がどのテナントに属するかは、サーバーがセッションから判断する。URL に含まれるテナント ID は画面の切り替えに使うだけで、セッションのテナントと一致しなければ拒否する |
| P3 | 読み書きは必ずテナント ID で絞り込む | テナントスコープのデータへのアクセスには、必ずセッションのテナント ID を条件に付ける。個々の処理で書き忘れないよう、データアクセスの共通部分で強制する（強制の仕組みは技術選定時に決める） |
| P4 | ファイルもテナントごとに分ける | 写真と席次表 PDF の保存先はテナント単位で分ける（例: `tenants/<tenantId>/photos/...`） |
| P5 | ファイルを公開しない | 写真と PDF は誰でもアクセスできる URL で公開しない。短時間だけ有効な URL を発行するか、アプリケーションを経由して配信する |
| P6 | UUID はアクセス制御ではない | テナント ID を知っていても、有効な参加トークンかセッションがなければアクセスできない。UUID が推測困難であることに安全性を頼らない |
| P7 | ログ・メトリクスにテナント ID を付ける | テナント単位で絞り込めるようにする（NFR-18） |
| P8 | 管理者はテナント横断 | 管理者はすべてのテナントを操作できる。管理操作は記録する（NFR-19） |

## URL の形式（仮置き）

| 用途 | URL の例 |
|---|---|
| 参加 URL（QR コード） | `https://<ゲスト用ドメイン>/join/<tenantId>?t=<参加トークン>` |
| ユーザー画面 | `https://<ゲスト用ドメイン>/t/<tenantId>/home` など |
| 管理面 | `https://<管理用ドメイン>/...` |

- 参加トークンは検証後にリダイレクトして URL から取り除く（[auth.md](auth.md)）
- 管理面はユーザー画面と別のオリジン（ドメイン）で提供し、Cookie などのセッション情報を共有しないようにする

## テナント間アクセスの確認観点

実装後、少なくとも次のことを確認する。

- テナント A のセッションで、テナント B の URL にアクセスすると拒否される
- テナント A のセッションで、テナント B の写真を指定した閲覧・いいね・保存が拒否される
- テナント A のタイムラインとランキングに、テナント B の写真が含まれない
- テナント A の参加トークンを使って、テナント B の参加 URL から参加できない
- 写真や PDF の配信 URL を流用しても、有効期限が切れた後はアクセスできない
