# 非機能要件

「出典」は、プロダクトオーナーが明示したもの（PO）か、本書で提案したもの（提案）かを示す。
提案の項目はレビューで確定させる。

## 一覧

| ID | 区分 | 要件 | 出典 | 関連 |
|---|---|---|---|---|
| NFR-01 | 対応環境 | 参加者は Web アプリケーションとして利用する。ネイティブアプリのインストールを不要とする | PO | — |
| NFR-02 | 対応環境 | 主な利用端末はスマートフォン。iOS / Android の標準的なブラウザで動作する（対象バージョンは要決定） | 提案 | — |
| NFR-03 | 対応環境 | QR コードは端末標準のカメラで読み取れる | 提案 | — |
| NFR-04 | 使いやすさ | 参加者の認証の手間をできるだけ省く。パスワード・メールアドレス・外部アカウントを求めない | PO | FR-G-01 |
| NFR-05 | 使いやすさ | QR コードを読み取ってからホームが表示されるまでに、参加者が行う操作はニックネームの入力だけにする | 提案 | FR-G-03 |
| NFR-06 | 使いやすさ | 幅広い年齢の参加者が使うことを想定し、文字の大きさとタップできる領域を十分に取る | 提案 | — |
| NFR-07 | 性能 | 写真の一覧は縮小画像で表示し、段階的に読み込む。オリジナル画像は拡大表示・保存のときだけ取得する | 提案 | FR-G-09, FR-G-12 |
| NFR-08 | 性能 | 乾杯やケーキ入刀などの演出の直後に、アクセスとアップロードが集中することを前提に設計する | 提案 | [OQ-01](../open-questions.md) |
| NFR-09 | 可用性 | 公開中のテナントの開催時間帯にサービスを止めない。メンテナンスは開催中のテナントがない時間帯に行う | 提案 | — |
| NFR-10 | 通信 | 式場の回線が不安定でも、アップロードの失敗が参加者に分かり、再試行できる | 提案 | FR-G-07 |
| NFR-11 | セキュリティ | 通信はすべて HTTPS で行う | 提案 | — |
| NFR-12 | セキュリティ | テナントは UUID で識別し、他のテナントのデータを参照・変更できない | PO | [design/multi-tenancy.md](../design/multi-tenancy.md) |
| NFR-13 | セキュリティ | 管理面は、権限を持つ Google アカウントだけが利用できる | PO | FR-A-01 |
| NFR-14 | セキュリティ | 参加 URL の流出に備え、参加トークンの有効期間の設定と再発行ができる | 提案 | FR-A-07, FR-A-08 |
| NFR-15 | プライバシー | 写真と席次表は、同じテナントの参加者と管理者だけが閲覧できる。検索エンジンにインデックスさせない | 提案 | — |
| NFR-16 | プライバシー | 写真に含まれる位置情報などのメタデータの扱いを定める | 提案 | [OQ-19](../open-questions.md) |
| NFR-17 | データ保持 | テナント終了後のデータの保持期間と削除方法を定める | 提案 | [OQ-13](../open-questions.md) |
| NFR-18 | 運用 | ログとメトリクスにテナント ID を付け、テナント単位で確認できる | PO（監視）+ 提案 | FR-A-09, FR-A-10 |
| NFR-19 | 運用 | 管理者の操作（テナントの作成・設定変更、参加 URL の再発行など）を記録する | 提案 | — |
| NFR-20 | コスト | ストレージ使用量と転送量をテナント単位で把握できる | 提案 | FR-A-10 |

## 想定規模（要決定）

規模によって技術選定と性能設計が変わるため、[OQ-01](../open-questions.md) で決める。

| 項目 | 値 |
|---|---|
| 1 テナントあたりの参加者数 | 要決定 |
| 1 テナントあたりの写真枚数 | 要決定 |
| 写真 1 枚あたりのファイルサイズ上限 | 要決定（[OQ-06](../open-questions.md)） |
| ピーク時の同時アクセス数（1 テナント） | 要決定 |
| 同じ日時に公開中になるテナント数 | 要決定 |
| 月あたりの新規テナント数 | 要決定 |
